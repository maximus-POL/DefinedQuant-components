# Security policy

## Reporting a vulnerability

**Do not open a public issue.**

Use GitHub's private vulnerability reporting on this repository (Security → Report a
vulnerability), or email **quant@defined.com**.

Please include what you found, how to reproduce it, and what you think the impact is. You will
get an acknowledgement within 72 hours. If the report is valid you will be credited in the fix
unless you ask not to be.

## Scope

In scope:

- code execution or injection through catalog content (contributed Markdown, YAML, or component
  source) reaching the website build or a visitor's browser
- supply-chain issues in this repository's dependencies or CI
- anything that lets contributed content escape the constraints in this document
- credential or secret exposure in the repository or its workflows

Out of scope:

- a component producing a numerically wrong answer — that is a
  [Method report](.github/ISSUE_TEMPLATE/report-method.yml), not a vulnerability
- findings that require a maintainer to merge malicious code deliberately

## Release security guarantees

These are implementation requirements for `v0.1.0`. They become release guarantees only after
the exact-commit checks demonstrate them.

1. **Contributed code is never executed during the Next.js website build, deployment job or page
   request.** Component imports and tests run only in isolated, least-privileged CI jobs with no
   production secrets.
2. **No MDX and no contributor-controlled HTML.** Markdown is rendered through a sanitising
   pipeline. Contributed content cannot introduce React or script.
3. **No arbitrary contributor SVG or remote embeds.** Components may return only the closed
   Pydantic `VisualizationSpec`; the trusted shared renderer escapes labels and emits no scripts,
   handlers, links, embedded HTML, or remote resources.
4. **Unknown fields under `display` in `contract.yaml` fail validation.** Presentation
   configuration is declarative data with a closed vocabulary.
5. **Constraints are evaluated by a closed operand/measure/operator set** — no `eval`, no `exec`,
   no dynamic
   import of contributed rules.
6. **Catalog generation is isolated from website deployment.** The catalog job may import
   component models to generate JSON Schema. It emits a static artefact and exact-SHA attestation;
   the separate private website consumes that artefact without importing Python.
7. **Deployment is artefact-only.** Only after required checks pass does a separate job receive
   the immutable static export and deployment credential. That job executes no contributor code.
8. **`main` is protected**: pull request and exact-SHA status checks are required; force pushes and
   deletion are blocked. External pull requests require maintainer review. A pull-request author
   cannot approve their own change, so maintainer-authored changes rely on the required exact-SHA
   checks until another maintainer can provide an independent approval.
9. **No arbitrary Python is executed through the public website**, now or later. A hosted
   execution service is out of scope for this project.

## Dependencies

- One runtime dependency: `pydantic`. Additions require an explicit decision and a licence check.
- Runtime compatibility is bounded (`pydantic>=2.7,<3` for the preview). Development and CI
  dependencies are locked; CI actions are pinned by full commit SHA.
- Dependency alerts are enabled and material vulnerabilities are addressed before the next
  release.
- A material dependency change is a revalidation trigger — see [VALIDATION.md](VALIDATION.md).

## Data

Test data is synthetic, seeded and generated by a committed script. No vendor data, no scraped
market series, no secrets, no personal data in the repository.
